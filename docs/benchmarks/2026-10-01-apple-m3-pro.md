按 GPU 分桶的真机帧节奏数据。**第二版**：第一版（同日早先）的数字是在后处理链空转时取的，全部作废；本版是链真正工作之后的复测，并补上了此前完全缺失的 WebGL2 两组。

## 方法

帧间隔由测量脚本自己的 `requestAnimationFrame` 循环在页面内采样，**不读运行时自己的计数器**。运行时的 `fps` / `droppedFrames` / `longFrames` 单独记录：

- `droppedFrames` 的定义是 `expectedFrames = max(1, round(raw × 60))`，即**按固定 60 Hz 预算累计**，从调度器启动起累加。它是累计值，不能当作掉帧率读。本文只记录它在窗口内的增量（`Δ dropped`）。
- `longFrames` 是超过 50 ms 的帧数，同样取窗口内增量（`Δ long`）。

`--dpr` 是必测项：DPR 1 下渲染目标是 Retina 面板的四分之一，全部锁 120 fps 说明不了什么。

复现命令见 [`README.md`](./README.md)。

### 怎么确认后处理真的在跑

这正是第一版栽的地方：链路"开着"，但什么都没画。所以本版在测之前先做两个独立检查，两者都必须通过。

1. **着色器与管线编译门禁**（`pnpm check:shaders`，有头 Chromium + 真 GPU）。六页 × 两条后端 12/12 编译干净；WebGPU 侧每页 16–23 个着色器模块、6–12 条渲染管线。第一版里 WebGPU 的 post 管线是**编译失败**的，而这个门禁会直接把它标红。
2. **「透传态 vs 关闭态」的像素残差**。`enabled: false` 的链路应当与完全不跑链路等价。实测残差 **0.92**（噪声地板 0.20，即同配置重复截图的残差）；作为对照，「开启 vs 关闭」的真实观感差异是 **12.35**。第一版这里测出来是 10.61 —— 也就是说"透传"和"关闭"差了整整一个数量级的观感差异，链路的输入是错的。

这两个检查都不是"看一眼截图觉得没问题"。门禁能给出确切的模块数与管线数，残差能给出一个数字，两者都可以在改动后重跑。

## 怎么读这些表

**WebGPU 侧，DPR 2 也守住了 120 fps。** 中位帧间隔 8.3 ms，`p95` ≤ 9.3 ms，2880×2000 的渲染目标上六页零超标帧（除 `liquid-glass` 的 2 帧）。这条结论之所以重要，是因为第一版在同一档位上给出了相反的答案——而后处理链一修好它就消失了。最可能的解释是：链路空转时那条路径每帧要做一次注定被拒的整帧拷贝，还要为"当前输出是谁"创建 canvas 尺寸的中间目标；把中间结果留在自建 render target 里、画布只由管线写之后，这些开销整个没了。**这个解释尚未被隔离验证**（没有做"只回退一处改动"的对照测量），所以只作为假设记录。

**WebGL2 侧，DPR 2 明显吃不住。** 六页里五页 `p50` 从 8.3 掉到 8.7–16.2 ms，四页出现 120/60 Hz 双峰台阶，`aurora-flow` 的 `max` 冲到 750 ms。分级系统在这里做了一件可观测的事：`aurora-flow` 被降到 **tier 2**，而它是唯一一页被降档的。这说明 tier 探测在真实负载下确实会动作，而不只是一个显示用的数字。

**`cursor-field` 的数字不能当负载数字读。** 它是指针驱动的场，而测量过程不产生指针输入，画布因此接近平坦（中心 400×400 区域只有 65 种颜色）。一个佐证：它在两条后端上的截图**直接残差是 0.000**——两个不同的光栅化器产出了字节级相同的 PNG，说明可见的画布基本是一片清屏色。它在两条后端上的 120 fps 都只描述"一个空闲页面"。

**`max` 与 `>16.7ms` 计数仍然不作为门禁指标。** 它们对系统噪声（GC、后台进程、截图本身）过于敏感：本版 `liquid-glass` 在 DPR 2 上出了 45.8 ms 的长帧，而它在 DPR 1 上 `max` 只有 10.2 ms。可以作为基线的只有 `p50` 与"是否出现 16.7 ms 台阶"。

**本版每组配置只跑了一次**，没有像第一版那样为 DPR 2 做两次运行来量化运行间方差。第一版测得的方差（`fps` 最多差 21.3%、`max` 差一倍以上）仍然适用，读数字时请保留这个量级的不确定性。

## 发现的缺陷

四个，**全部已修**。都是既有问题，都不被当时的测试覆盖，都只在真机 GPU 上可见。

### 1. 强制 WebGL2 回退路径每帧抛异常（P0 · ✅ 已修）

`/?demo=<page>&backend=webgl` 下，每一帧抛出一次 `TypeError: Invalid value used as weak map key`。

**根因**（堆栈 + three 源码 + 本项目源码三处对齐后确认）：

- `packages/post/src/postProcessing.ts` 的 `captureDepth()` 调用 `renderer.copyTextureToTexture(depthTexture, historyDepthTexture)`。
- 目的地 `historyDepthTexture` 是 `new DepthTexture(1, 1)`，一个**没有挂在任何 render target 上的裸深度纹理**。
- three 的 WebGL 后端把深度纹理拷贝实现为两个纹理各自 render target 的 framebuffer 之间的 `blitFramebuffer`。它先做 `backend.get(dstTexture)`，再取 `dstTextureData.renderTarget` —— 裸纹理的这份数据是空对象，`renderTarget` 为 `undefined`，接着 `backend.get(undefined)` 执行 `WeakMap.set(undefined, {})` 并抛错。
- WebGPU 后端的 `copyTextureToTexture` 是真正的纹理对纹理拷贝，不需要 framebuffer，所以只有 WebGL2 会炸。

**为什么统计属性也是空的**：调用点在 `packages/renderer/src/glassLayer.ts` 的 `renderFrame` 里，顺序是

```
renderer.setRenderTarget(this.backdropRT);
this.postProcessing?.captureDepth(renderer);   // ← 在这里抛
renderer.setRenderTarget(null);                // ← 永远执行不到
```

抛出后 render target 停留在 `backdropRT`，此后每一帧都渲染进 backdrop 的离屏目标，**永远回不到 canvas**。同时 `frame()` 里在 `renderFrame` 之后的 `reportStats()` 也被跳过，因此 `onStats` 从不触发，React stage 上的 `data-ui-lib-backend` / `data-ui-lib-tier` / `data-ui-lib-fps` 等属性全部为空。

> **更正**：本节初稿把截图里"背后的世界整块是黑的"也归因于这次崩溃。**这是错的。** 崩溃修好之后世界仍然缺失，见缺陷 3——崩溃与黑屏是两个独立问题。

**为什么没被测出来**：`tests/e2e/acceptance.spec.ts` 的 WebGL 路由用例只断言 DOM 语义（stage 到达 `ready`、canvas 存在、可聚焦链接）。帧回调抛异常不影响这些断言，所以用例全绿。

**修法**：给历史深度纹理配一个只作宿主、从不被绘制的 `RenderTarget`，并在拷贝前用 three 的公开方法 `renderer.initRenderTarget(host)` 预建它的 framebuffer。第一次尝试用 `renderer.setRenderTarget(host)` **无效**——它只写 `_currentRenderTarget`，不触发 `_textures.updateRenderTarget()` → `_renderContexts.get()` → `backend.initRenderTarget()` 这条链，framebuffer 从未被创建，深度纹理也没登记进 `backend` 的纹理表。`initRenderTarget` 在 three 内部没有任何调用点，专供调用方预建。`setSize()` 只缩放颜色附件、不同步 `depthTexture`，所以深度尺寸单独跟踪。

**验证**：`Invalid value used as weak map key` 从 693 次降到 **0**；`data-ui-lib-backend` 由 `unknown` 恢复为 `webgl2`，`tier=3`、`fps=120.0`、`resources=11`。

### 2. WebGPU 下 post 的时间性链路是死的（P1 · ✅ 已修，修法后又被替换）

WebGPU 路由下控制台每秒出现约 115 次：

```
THREE.WebGPUBackend: copyFramebufferToTexture: Source and destination formats do not match. rgba16float bgra8unorm
```

**根因**：`postProcessing.ts` 的 `commit()` 调用 `renderer.copyFramebufferToTexture(historyTexture)`，而 `historyTexture = new FramebufferTexture(1, 1)` 的 GPU 格式跟着 canvas（`bgra8unorm`），当前绑定的目标却是 post 链的半浮点中间目标（`rgba16float`）。three 的 WebGPU 后端在格式不匹配时**只警告并直接返回**，不做拷贝。

紧接着 `commit()` 无条件执行 `uniforms.historyValid.value = 1`——**声称一份从未被写入的历史是有效的**。

**当时的修法**：新增 `framebufferCopyWouldFail()`，逐字镜像 three 自己的源上下文查找（`_currentRenderContext` → `_renderTarget` → `_getFrameBufferTarget()`，**不是** `getRenderTarget()`——后者在渲染管线内部目标仍绑定时报 null），在拷贝会被拒绝时把 `historyValid` 置 0 并 return。第一次尝试直接读 `getRenderTarget()` **无效**——诊断输出是 `source= bgra8unorm dest= bgra8unorm`（看起来匹配、于是放行），而 three 实际报的是 `rgba16float` / `bgra8unorm`。照抄这条链之后，诊断输出与 three 的警告一字不差。

**验证**：警告从 **698 行降到 10 行**（每秒约 115 次 → 1 次）。

> **这份守卫现已删除**，见缺陷 3 的修法。它是对 three 私有实现的逐字抄写，只解决"拷贝被拒后不要谎报历史有效"，不解决"拷错了源"。改成由调用方显式传入源纹理、格式在构造期对齐之后，事后判定的必要前提消失了。教训：**镜像私有实现的补丁是临时脚手架，不是终点**——它的存在本身就在提示上游的调用契约用错了。

### 3. post 链在两条后端上都没在干活（P0 · ✅ 已修）

这一条比前两条严重：**post 链从来没有真正生效过**，两条后端各坏各的。前两条修好之后画面暴露了 WebGL2 的那一半，顺着它追下去才挖到 WebGPU 的那一半。

#### 3a. WebGL2：画面全黑

缺陷 1 修好、崩溃归零之后，强制 WebGL2 的页面**仍然**只有 DOM 与玻璃面板：透镜、晶体、辉光、轨道线全部不见。此时 `data-ui-lib-backend` 已经是 `webgl2`、`tier=3`、`fps=120.0`、`resources=11`——**帧在跑，统计健康，只是画面缺了整块世界**。

**定位实验（依次排除，每步一次真机截图）**：

1. 临时关掉 post 链 → 世界完整出现。说明 **WebGL2 的场景渲染本身是好的，是 post 链把背景吃掉的**。
2. post 链保留、把 `enabled` 默认改成 `false`（输出退化为对 `viewportTexture()` 的纯透传）→ **仍然全黑**。所以问题不在 bloom / 色散 / TAA 任何一步特效，而在链的**输入**。
3. 把 `outputNode` 固定成常量红 `vec4(1,0,0,1)` → **整块画布变红**。管线的最终写入完全正常。
4. 输出 `vec4(uv.x, uv.y, baseSample.r, 1)` → UV 渐变完全正确，**蓝通道（即采样值）恒为 0**。UV 对、写入对、采样是空的。

**根因**：`glassLayer.renderFrame()` 逐帧切换 `renderer.toneMapping` / `renderer.outputColorSpace`，想把中间缓冲保持在 working-linear 空间。而 three 的这两个设置会翻转 `Renderer.needsFrameBufferTarget`：

```js
get needsFrameBufferTarget() {
  const useToneMapping = this.currentToneMapping !== NoToneMapping;
  const useColorSpace = this.currentColorSpace !== ColorManagement.workingColorSpace;
  return useToneMapping || useColorSpace;
}
```

- 步骤 1–4 期间（`outputColorSpace = LinearSRGBColorSpace`、`toneMapping = NoToneMapping`）→ `needsFrameBufferTarget === false` → 画布这一趟**直接画进画布**，不走 three 的内部 framebuffer target。
- 步骤 5 之前把设置恢复 → `needsFrameBufferTarget` 变回 `true` → `copyFramebufferToTexture()` 解析出的源是 `this._renderTarget || this._getFrameBufferTarget()`，即那个**从没被写过**的内部 target。

于是一次没发生的拷贝被当成"当前画布"，整条链拿到一张空图。同一条链在 WebGPU 上"看起来正常"，只是因为 WebGPU 的管线根本编译不过（见 3b），管线什么都没写，画布留住了步骤 3–4 的原始画面。

#### 3b. WebGPU：post 管线根本编译不过，链路静默空转

WebGPU 路由下控制台稳定出现：

```
THREE.WebGPURenderer: Render pipeline creation failed (renderPipeline_RenderPipeline_17):
  An error occurred while generating Tint IR
  error: swizzle view instruction still has usages after lowering
 - While getting fragment MTLFunction for [RenderPipeline "renderPipeline_RenderPipeline_17"]
```

**决定性实验**：临时关掉 post 链 → 这条错误与它引发的 `Invalid RenderPipeline` / `Invalid CommandBuffer` 一串校验错误**全部消失**。所以失败的 `renderPipeline_17` 就是 post 管线。

**后果**：管线创建失败后 three 只打日志，每帧照旧提交一个 invalid command buffer，**没有任何异常抛给调用方**。于是：

- 画布上看到的是步骤 3–4 的原始合成结果，**没有 bloom、没有色散、没有 TAA**。
- `commit()` 同样报 `Source and destination formats do not match. rgba16float bgra8unorm`：它拷的也是那个 `rgba16float` 内部 target，不是画布。

#### 3c. Tint 降级失败的根因

把判定器做成三件套之后定位到的：patch `GPUDevice.prototype.createShaderModule` 截获 WGSL、用 `createRenderPipelineAsync({ layout: "auto" })` + `popErrorScope` 单独复现、再对着 WGSL 做**语句级双向二分**（逐条删 / 逐条留，看错误在哪一侧消失）。

**结论**：TSL 把**每个中间结果**都落到模块级 `var<private> nodeVarN`，而"从 swizzle 再取分量"的嵌套形式（`vec3<f32>(v.xyz.y, …)`，其中 `v` 是模块级私有变量）会让 Tint 的降级后使用计数失衡，报 `swizzle view instruction still has usages after lowering`。**同一表达式写在函数内 `let` 上就通过。**

这不是 three 的 bug，是 TSL 在模块级私有变量上的一种组合限制。修法是让色散基准改走 `resolved.g`，避开嵌套 swizzle。

顺带确认了一件对判定很重要的事：**同一份 WGSL 在 Metal 适配器上失败、在 SwiftShader 适配器上通过**。所以无头 CI 永远抓不到这类失败——门禁必须是有头 + 真 GPU。这一条直接决定了 `pnpm check:shaders` 刻意不进 CI。

#### 3d. 修法

两半一起修：

- **步骤 3–4 合成到自建的 `compositeRT`**（`packages/renderer/src/glassLayer.ts`）。post 链从 `compositeRT.texture` 采样，画布只由 `RenderPipeline` 写；没有 post 时由 Node 版全屏 quad 搬一次。render target 渲染天然是 working-linear、无 tone mapping，所以那两行逐帧切换**整个删掉**——缺陷 3a 的入口不存在了。
- **`@ui-lib/post` 新增 `sourceTexture` 选项**，由调用方显式交出"这一层后处理之前的合成结果"；`commit()` 改用 `renderer.copyTextureToTexture(sourceTexture, historyTexture)`，源与历史缓冲的 `format` / `type` / `colorSpace` 在构造期逐字段对齐。`sourceTexture` 为空时 `commit()` 把 `historyValid` 置 0 直接返回。
- **「深度解算 + 时间累积」上移到效果链之前。** 画布不可回读之后历史从 `compositeRT` 拷贝，若仍把 TAA 留在链尾，就会把"后处理过的值（含颗粒）"与原始值按 0.88 反馈相混，几乎抵消整条链。颗粒与暗角留在解析之后——颗粒是逐帧图案，回灌进历史只会被平均掉。选项语义不变：`temporalBlend` 仍只在历史有效时生效。

**验证**：`pnpm check:shaders` 12/12 编译干净；「透传态 vs 关闭态」残差 0.92；WebGL2 世界完整恢复（与 WebGPU 版直接残差 0.538）。

### 4. 自有 render target 的 UV 上下翻转（P0 · ✅ 已修）

缺陷 3 修好之后画面上下颠倒，而**分界线在画面正中**。

**判定过程**：截图看起来像"构图错了"而不是"图像翻了"，试过 `rotate(180)`（残差 21.93）与 `FLIP_LEFT_RIGHT`（24.69）都不对；扫描"绕不同水平轴翻转"后定位到**绕画面正中 y=450 翻转**（残差 1.32）——分界线在画面中部，这正是"只翻了 UV"而非"整页转了 180°"的特征。

**根因**：three 按 GL 约定自下而上存储 render target 纹理，而链用 `screenUV`（自上而下）去采样它。node builder 的 `isFlipY()` 在 **WebGPU 与 WebGL 两条路径上都不提供有效补偿**：

| 实现 | 位置 | 返回 |
|---|---|---|
| `NodeBuilder.isFlipY()` | `nodes/core/NodeBuilder.js:1214` | `false`（抽象基类） |
| `WGSLNodeBuilder.isFlipY()` | `renderers/webgpu/nodes/WGSLNodeBuilder.js:1670` | `false` |
| `GLSLNodeBuilder.isFlipY()` | `renderers/webgl-fallback/nodes/GLSLNodeBuilder.js:1470` | `true` |

`TextureNode.setupUV` 只在 `builder.isFlipY()` 为真时才考虑翻转，且翻转与否由 `_flipYUniform` 决定，而它的赋值条件是 `texture.image instanceof ImageBitmap && flipY === true`、或 `isRenderTargetTexture` / `isFramebufferTexture` / `isDepthTexture` 为真。所以 WebGL2 那条路**看起来**会翻、WebGPU 那条路一定不翻——但实测结果是**两条后端都没有翻**（见下）。

**修法**：显式 `vec2(screenUV.x, oneMinus(screenUV.y))`；源纹理、深度纹理、历史纹理、采样偏移与 reprojection clip 全部改用该空间（`viewportTexture()` 回退路径仍用 `screenUV`）。

**判定指标**：用「透传态 vs 关闭态」的像素残差——`enabled: false` 的链路应当等价于完全不跑链路。

| 对比 | 修复前 | 修复后 |
|---|---|---|
| `passthru` vs `post-off`（应≈0，噪声地板） | 10.61 | **0.92** |
| `post-on` vs `post-off`（后处理真实增益） | 19.68 | **12.35** |

**两条后端的一致性复核**（修好之后，六页全部比对）：

| page | 直接残差 | 竖向翻转后 | 旋转 180° | 水平镜像 |
|---|---|---|---|---|
| liquid-glass | **0.538** | 12.467 | 17.924 | 14.348 |
| product-hero | **2.641** | 14.750 | 22.155 | 22.013 |
| scroll-cinema | **3.772** | 35.177 | 52.221 | 48.945 |
| cursor-field | **0.000** | 10.619 | 14.611 | 14.902 |
| aurora-flow | **5.376** | 23.328 | 27.395 | 25.435 |
| wake | **6.020** | 16.392 | 26.596 | 26.856 |

六页的直接残差都是最低项，且比翻转项低一个数量级。所以：**WebGPU 与 WebGL2 的画面朝向一致，`oneMinus` 在两条后端上都正确，不存在双重翻转。** 这是"读源码推测"与"实测"分歧时该信哪一个的例子——源码读出来的结论是 WebGL2 会被翻转，实测不是。
