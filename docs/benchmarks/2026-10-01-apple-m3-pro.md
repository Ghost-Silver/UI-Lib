# 真机测量记录 · 2026-10-01 · Apple M3 Pro / Metal

第一份按 GPU 分桶的真机帧节奏数据。同时暴露了三个此前所有 CI 与验收用例都没能发现的缺陷，见文末「发现的缺陷」：前两个已修，第三个一路追下去发现比预想严重——**post 链在两条后端上都没在干活**，WebGL2 画面全黑、WebGPU 管线根本编译不过。因此本文的帧节奏数字只描述场景本身，不包含后处理。

## 方法

帧间隔由测量脚本自己的 `requestAnimationFrame` 循环在页面内采样，**不读运行时自己的计数器**。运行时的 `fps` / `droppedFrames` / `longFrames` 单独记录：

- `droppedFrames` 的定义是 `expectedFrames = max(1, round(raw × 60))`，即**按固定 60 Hz 预算累计**，从调度器启动起累加。它是累计值，不能当作掉帧率读。本文只记录它在窗口内的增量（`Δ dropped`）。
- `longFrames` 是超过 50 ms 的帧数，同样取窗口内增量（`Δ long`）。

`--dpr` 是必测项：DPR 1 下渲染目标是 Retina 面板的四分之一，全部锁 120 fps 说明不了什么。

复现命令见 [`README.md`](./README.md)。

### 怎么读这两张表

**稳定的部分**：所有页、两次运行，中位帧间隔都是 8.3–8.5 ms，即**恰好一个 120 Hz vsync 周期**。DPR 2 下没有一个页面出现"稳定掉到 60 Hz"的中位值——`p50` 从未接近 16.7 ms。这说明瓶颈不是持续吞吐，而是**离散卡顿**：绝大多数帧轻松在预算内，损失来自偶发的长帧。

**不稳定的部分**：`fps`（由均值推出）在两次运行之间最多差 **21.3%**（wake：82.8 → 100.4），`max` 差得更多（scroll-cinema：150.1 → 58.4，第一次的 150 ms 长帧没有复现）。`>16.7ms` 的计数同样大幅波动。

因此本记录**不把 `max`、`>16.7ms` 计数当作门禁指标**。它们对系统噪声（GC、后台进程、截图本身）过于敏感。可以作为基线的只有 `p50` 与"是否出现 16.7 ms 台阶"。

**DPR 2 的双峰现象**：未锁 120 fps 的页面，其 `p95`/`p99` 稳定落在 16.7–17.6 ms，即帧间隔在 8.4 ms 与 16.8 ms 之间交替——120 Hz 与 60 Hz 两个节奏混用。DPR 2 下两次运行中分别有 1 页和 5 页出现这个台阶；`cursor-field` 两次都完整锁住 120 fps。

## 发现的缺陷

测量过程本身暴露了三个缺陷。三个都是**既有问题**，与本次改动无关；三个都不被现有测试覆盖；三个都只在真机 GPU 上才可见。前两个已修，第三个是修好前两个之后才显形的，而且比前两个都严重。

### 1. 强制 WebGL2 回退路径每帧抛异常（P0 · ✅ 已修）

`/?demo=<page>&backend=webgl` 下，每一帧抛出一次 `TypeError: Invalid value used as weak map key`。

**根因**（堆栈 + three 源码 + 本项目源码三处对齐后确认）：

- `packages/post/src/postProcessing.ts` 的 `captureDepth()` 调用 `renderer.copyTextureToTexture(depthTexture, historyDepthTexture)`。
- 目的地 `historyDepthTexture` 是 `new DepthTexture(1, 1)`，一个**没有挂在任何 render target 上的裸深度纹理**。
- three 的 WebGL 后端把深度纹理拷贝实现为两个纹理各自 render target 的 framebuffer 之间的 `blitFramebuffer`。它先做 `backend.get(dstTexture)`，再取 `dstTextureData.renderTarget` —— 裸纹理的这份数据是空对象，`renderTarget` 为 `undefined`，接着 `backend.get(undefined)` 执行 `WeakMap.set(undefined, {})` 并抛错。
- WebGPU 后端的 `copyTextureToTexture` 是真正的纹理对纹理拷贝，不需要 framebuffer，所以只有 WebGL2 会炸。

**为什么统计属性也是空的**：调用点在 `packages/renderer/src/glassLayer.ts` 的 `renderFrame` 里，顺序是

```
renderer.setRenderTarget(this.backdropRT);
this.postProcessing?.captureDepth(renderer);   // ← 在这里抛
renderer.setRenderTarget(null);                // ← 永远执行不到
```

抛出后 render target 停留在 `backdropRT`，此后每一帧都渲染进 backdrop 的离屏目标，**永远回不到 canvas**。同时 `frame()` 里在 `renderFrame` 之后的 `reportStats()` 也被跳过，因此 `onStats` 从不触发，React stage 上的 `data-ui-lib-backend` / `data-ui-lib-tier` / `data-ui-lib-fps` 等属性全部为空。

> **更正**：本节初稿把截图里"背后的世界整块是黑的"也归因于这次崩溃。**这是错的。** 崩溃修好之后世界仍然缺失，见缺陷 3——崩溃与黑屏是两个独立问题。

**为什么没被测出来**：`tests/e2e/acceptance.spec.ts` 的 WebGL 路由用例只断言 DOM 语义（stage 到达 `ready`、canvas 存在、可聚焦链接）。帧回调抛异常不影响这些断言，所以用例全绿。

**修法**：给历史深度纹理配一个只作宿主、从不被绘制的 `RenderTarget`，并在拷贝前用 three 的公开方法 `renderer.initRenderTarget(host)` 预建它的 framebuffer。第一次尝试用 `renderer.setRenderTarget(host)` **无效**——它只写 `_currentRenderTarget`，不触发 `_textures.updateRenderTarget()` → `_renderContexts.get()` → `backend.initRenderTarget()` 这条链，framebuffer 从未被创建，深度纹理也没登记进 `backend` 的纹理表。`initRenderTarget` 在 three 内部没有任何调用点，专供调用方预建。`setSize()` 只缩放颜色附件、不同步 `depthTexture`，所以深度尺寸单独跟踪。

**验证**：`Invalid value used as weak map key` 从 693 次降到 **0**；`data-ui-lib-backend` 由 `unknown` 恢复为 `webgl2`，`tier=3`、`fps=120.0`、`resources=11`。

### 2. WebGPU 下 post 的时间性链路是死的（P1 · ✅ 已修）

WebGPU 路由下控制台每秒出现约 115 次：

```
THREE.WebGPUBackend: copyFramebufferToTexture: Source and destination formats do not match. rgba16float bgra8unorm
```

**根因**：`postProcessing.ts` 的 `commit()` 调用 `renderer.copyFramebufferToTexture(historyTexture)`，而 `historyTexture = new FramebufferTexture(1, 1)` 的 GPU 格式跟着 canvas（`bgra8unorm`），当前绑定的目标却是 post 链的半浮点中间目标（`rgba16float`）。three 的 WebGPU 后端在格式不匹配时**只警告并直接返回**，不做拷贝。

紧接着 `commit()` 无条件执行 `uniforms.historyValid.value = 1`——**声称一份从未被写入的历史是有效的**。`packages/post/src/depthCopy.ts` 的文档注释里已经把这条拷贝路径记为失败路径，但 `commit()` 仍在走它。

同一路由下另有一个 render pipeline 编译失败（`An error occurred while generating Tint IR: swizzle view instruction still has usages after lowering`），随后每帧提交一个 invalid command buffer。

**影响**：由于 `enabled` 默认为 `true`、`temporalBlend` 默认为 `0.88`，TAA 的时域混合路径是被启用的。当前画面看起来正常，说明混合权重被其它因子（`depthConfidence` / `uncoveredMotion` 等）压到了 0 附近；但这是巧合，不是设计。**这也意味着本次测到的 120 fps 是一个上限，而不是典型值**——post 链的时间性部分实际没有工作。

**修法**：新增 `framebufferCopyWouldFail()`，逐字镜像 three 自己的源上下文查找，在拷贝会被拒绝时把 `historyValid` 置 0 并 return。第一次尝试直接读 `getRenderTarget()` **无效**——诊断输出是 `source= bgra8unorm dest= bgra8unorm`（看起来匹配、于是放行），而 three 实际报的是 `rgba16float` / `bgra8unorm`。原因是 `Renderer.copyFramebufferToTexture` 用的是私有 `this._currentRenderContext.renderTarget`，并且有 `_currentRenderContext` → `_renderTarget` → `_getFrameBufferTarget()` 三级回退；`getRenderTarget()` 在渲染管线内部目标仍绑定时报 null。照抄这条链之后，诊断输出与 three 的警告一字不差。声明一份不存在的历史比不声明更糟，所以格式不可判定时保留原行为（尝试拷贝）。

**验证**：警告从 **698 行降到 10 行**（每秒约 115 次 → 1 次；剩下那次是首帧帧缓冲纹理尚未登记、无法判定格式）。

### 3. post 链在两条后端上都没在干活（P0 · 🔴 未修）

这一条比前两条严重，而且是一路追下来才看清的：**post 链从来没有真正生效过**，两条后端各坏各的。前两条修好之后画面暴露了 WebGL2 的那一半，顺着它追下去才挖到 WebGPU 的那一半。

#### 3a. WebGL2：画面全黑

缺陷 1 修好、崩溃归零之后，强制 WebGL2 的页面**仍然**只有 DOM 与玻璃面板：透镜、晶体、辉光、轨道线全部不见，`screenshots/liquid-glass-webgl2-dpr2-broken.png` 描述的画面没有恢复。此时 `data-ui-lib-backend` 已经是 `webgl2`、`tier=3`、`fps=120.0`、`resources=11`——**帧在跑，统计健康，只是画面缺了整块世界**。

**定位实验（依次排除，每步一次真机截图）**：

1. 临时关掉 post 链（`if (false && this.postOptions !== false …)`）→ 世界完整出现。说明 **WebGL2 的场景渲染本身是好的，是 post 链把背景吃掉的**。（临时补丁已撤销，`git diff` 为空。）
2. post 链保留、把 `enabled` 默认改成 `false`（输出退化为对 `viewportTexture()` 的纯透传）→ **仍然全黑**。所以问题不在 bloom / 色散 / TAA 任何一步特效，而在链的**输入**。
3. 把 `outputNode` 固定成常量红 `vec4(1,0,0,1)` → **整块画布变红**。管线的最终写入完全正常。
4. 输出 `vec4(uv.x, uv.y, baseSample.r, 1)` → UV 渐变完全正确，**蓝通道（即采样值）恒为 0**。UV 对、写入对、采样是空的。

**根因**：`glassLayer.renderFrame()` 逐帧切换 `renderer.toneMapping` / `renderer.outputColorSpace`，想把中间缓冲保持在 working-linear 空间。而 three 的这两个设置会翻转 `Renderer.needsFrameBufferTarget`：

```js
get needsFrameBufferTarget() {
  const useToneMapping = this.currentToneMapping !== NoToneMapping;
  const useColorSpace = this.currentColorSpace !== ColorManagement.workingColorSpace;
  return useToneMapping || useColorSpace;
}
```

- 步骤 1–4 期间（`outputColorSpace = LinearSRGBColorSpace`、`toneMapping = NoToneMapping`）→ `needsFrameBufferTarget === false` → 画布这一趟**直接画进画布**，不走 three 的内部 framebuffer target。
- 步骤 5 之前把设置恢复 → `needsFrameBufferTarget` 变回 `true` → `copyFramebufferToTexture()` 解析出的源是 `this._renderTarget || this._getFrameBufferTarget()`，即那个**从没被写过**的内部 target。

于是一次没发生的拷贝被当成"当前画布"，整条链拿到一张空图。同一条链在 WebGPU 上"看起来正常"，只是因为 WebGPU 的管线根本编译不过（见 3b），管线什么都没写，画布留住了步骤 3–4 的原始画面。

**验证过的修法（本轮未提交）**：不再依赖 `copyFramebufferToTexture` 去猜"当前输出是谁"。把步骤 3–4 合成到一个显式的 render target（`compositeRT`），post 链采样 `compositeRT.texture`，画布只由 `RenderPipeline` 写。render target 渲染天然就是 working-linear、无 tone mapping，所以那两行逐帧切换可以整个删掉。真机验证：**WebGL2 的世界完整恢复**（`?demo=liquid-glass&backend=webgl` 与 WebGPU 版逐像素接近），控制台零错误，`fps=120.0`。

**为什么没有提交**：这个修法同时把 WebGPU 暴露成黑屏——因为它的 post 管线本来就编译不过（3b）。修好次后端、弄坏主后端，不是一笔划算的账。两半必须一起修。

#### 3b. WebGPU：post 管线根本编译不过，链路静默空转

WebGPU 路由下控制台稳定出现：

```
THREE.WebGPURenderer: Render pipeline creation failed (renderPipeline_RenderPipeline_17):
  An error occurred while generating Tint IR
  error: swizzle view instruction still has usages after lowering
 - While getting fragment MTLFunction for [RenderPipeline "renderPipeline_RenderPipeline_17"]
```

**决定性实验**：临时关掉 post 链 → 这条错误与它引发的 `Invalid RenderPipeline` / `Invalid CommandBuffer` 一串校验错误**全部消失**。所以失败的 `renderPipeline_17` 就是 post 管线。

**后果**：管线创建失败后 three 只打日志，每帧照旧提交一个 invalid command buffer，**没有任何异常抛给调用方**。于是：

- 画布上看到的是步骤 3–4 的原始合成结果，**没有 bloom、没有色散、没有 TAA**。
- `docs/benchmarks` 里 WebGPU 那几组 120 fps 数字，描述的是"场景 + 空的 post 链"，不是完整管线。**它们是上限，不是典型值**——这一点此前只写在了缺陷 2 的注脚里，实际比那更彻底。
- `commit()` 同样报 `Source and destination formats do not match. rgba16float bgra8unorm`：它拷的也是那个 `rgba16float` 内部 target，不是画布。缺陷 2 的守卫挡住了"声明假历史"，但没解决"拷错源"。

**已排除**：把 post 图里的深度纹理采样换成常量，错误依旧——触发点不在深度采样这一处。

**待决**：`swizzle view instruction still has usages after lowering` 是 Dawn/Tint 的降级失败，需要定位是 TSL 图里哪一种纹理采样 + swizzle 组合触发（候选：多个 `texture()` 结果之间取 `.r` / `.b` 拼 `vec3`、`historyTexture` 的 `vec4` 与 `historyDepthTexture` 的标量混用），再决定是改图、绕开，还是向 three 报 issue。
